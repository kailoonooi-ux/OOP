Welcome

Understand OOP well enough to use it on any test question

Memorising definitions isn't enough. In a practical test you'll get a new problem, such as a library, a car park or a payroll, and you'll have to decide which classes to write and which pillar fits where. This tutorial trains exactly that skill.

The 4 pillars — remember them as A·P·I·E

A

Abstraction

Show what it does, hide how.

 P

Polymorphism

One call, many behaviours.

 I

Inheritance

A child class is a kind of parent and reuses its code.

 E

Encapsulation

Lock up the data. Only allow safe changes.

We'll learn them in the order E → I → P → A, because each one builds on the one before.

Pillar 1 of 4 · E

  
🔒 Encapsulation

  
Keep an object's data private. Let the outside world change it only through methods and properties that check the rules.

  
🏧
Think of an ATM. You can't open the machine and grab the cash, because the money is private. You can only press buttons such as Withdraw and Deposit, and the machine checks your PIN and balance before it does anything. The buttons are the public methods. The cash box is the private field.

📝 How to explain it in a test answer

  "Encapsulation means bundling data and the methods that act on it inside a class, and hiding the data using private. Access goes through public properties and methods that enforce rules. For example, _balance is private and Withdraw() rejects amounts greater than the balance. Benefit: the object can never be in an invalid state, and the internal details can change without breaking other code."


  
⚠️ Common mistakes
    
    
  • Making fields public "to make it easier". That defeats the purpose.
    • 
    
  • Writing a setter with no checks: set { _score = value; } is technically encapsulated but protects nothing. If the question gives a rule, put it in the setter.
    • 
    
  • Getting edge cases wrong: "between 0 and 100" usually includes 0 and 100, so use >= and <=.
    • 
    
  • Writing Score = value; inside the Score setter. That calls itself forever and crashes with a StackOverflow. Store into the field instead: _score = value;
    • 
  


  
🔍 How to spot it in a question
Look for words like "must not be negative", "cannot be changed after creation", "only between…", "read-only" or "validate". Each one is an encapsulation rule, so it needs a private field and a checked property or method.

Pillar 2 of 4 · I

  
🧬 Inheritance

  
A child class is a more specific kind of its parent class. It gets all the parent's members for free, then adds its own.

  
🎮
Think of a role-playing game. Every character has a Name and Health and can take damage. A Warrior is a Character with extra Strength. A Mage is a Character with extra Mana. Instead of copying Name/Health/TakeDamage into every class, you write them once in Character and let the children inherit them.


  
The code

  


  

    
Key syntax
    
      
  • class Warrior : Character means Warrior inherits from Character.
    • 
      
  • : base(name, 150) runs the parent's constructor first.
    • 
      
  • protected means the member is visible to the class and its children, but not to outsiders.
    • 
      
  • C# allows only one parent class: class A : B, C is not allowed if B and C are both classes.

    Interactive: "is-a" or "has-a"?
    
  
    This is the most important design decision. Only use inheritance when the child is a kind of parent. If one thing has a part, make that part a field instead (this is called composition).
    
  
    

  
    📝 How to explain it in a test answer
    
  "Inheritance lets a class (the subclass) acquire the fields and methods of another class (the base class), forming an is-a relationship. For example, class Warrior : Character means Warrior inherits Name, Health and TakeDamage, then adds Strength. Benefit: code reuse, since common code is written once and a change in the base class applies to every subclass."
    

  
    ⚠️ Common mistakes
      
    
    • Forgetting : base(...) when the parent constructor needs arguments. This gives compile error CS7036: "There is no argument given that corresponds to the required parameter…"
      • 
    
    • Copying the parent's properties into the child "just to be safe". This creates duplicate or hidden members, which is exactly what inheritance is meant to avoid.
      • 
    
    • Using inheritance for "has-a": class Car : Engine ❌. A Car has an Engine, so use private Engine _engine;
      • 
    
    • Trying to use a parent's private field in the child. Children can't see private members, so make it protected or use a property.
      •

    Pillar 3 of 4 · P
    
  
    🎭 Polymorphism
    
  
    "Many forms": you make the same call on different objects, and each one responds in its own way.
    
  
    📣
    A teacher says "Everyone, attack!" to the whole party. The teacher doesn't need to know who is who. The Warrior swings a sword, the Mage casts a fireball and the Cleric smites. It's one instruction with many behaviours. In code: foreach (Character c in party) c.Attack();
    

  
    The code: virtual + override

    💡 What just happened?
    The variable type is Character, but the object is a Warrior, Mage or Cleric. With virtual/override, C# checks the real object at runtime and runs that version. That's why the loop never needs if (c is Warrior) … else if (c is Mage) …. Adding a new character type, such as Archer, needs zero changes to the loop.

    Also, run it 4+ times with a Mage. When its mana runs out, it calls base.Attack(), which reuses the parent's version from inside the override.
    

  
    Two kinds of polymorphism
    
  
    
    
    Runtime (overriding) ⭐ the main one
    
      
    Same method signature in parent and child. The parent marks it virtual (or abstract) and the child uses override. The version is chosen while the program runs, based on the real object.
    
    
    Compile-time (overloading)
    
      
    Same method name with different parameters in the same class. The compiler picks one based on the arguments you pass.
    
      
    
  
    

  
    ⚠️ The trap examiners love: new vs override
    
  
    
  
    

  
    📝 How to explain it in a test answer
    
  "Polymorphism means objects of different classes can be treated through a common base type, and the same method call produces behaviour specific to each object's actual class. In C# this is done with virtual methods in the base class and override in the subclasses. For example, calling c.Attack() on each item of a List<Character> runs the Warrior's or Mage's version. Benefit: new subclasses can be added without changing the code that uses them."
    

  
    ⚠️ Common mistakes
      
    
    • Forgetting virtual in the parent. Then override gives error CS0506: "cannot override inherited member because it is not marked virtual, abstract, or override".
      • 
    
    • Changing the signature: override decimal CalculatePay(int bonus) doesn't match the parent's CalculatePay(), so it's a different method.
      • 
    
    • Writing if (e is Manager) … else if (e is Intern) … in the loop. It works, but it's not polymorphism, and in a test it shows you didn't use the concept.
      •

    Pillar 4 of 4 · A
    
  
    🎛️ Abstraction
    
  
    Show what an object can do and hide how it does it. Define a contract with abstract classes or interfaces.
    
  
    🚗
    Driving a car: you only need the steering wheel, accelerator and brake. You don't need to know how fuel injection works. The pedals are the abstraction, a simple "what". The engine is the hidden "how". You can drive a petrol car or an electric car with the same pedals, because both follow the same contract.
    

  
    Encapsulation vs Abstraction — the classic confusion
    
  Encapsulation is about protecting data: private fields plus validated access. It's the "how it's kept safe".
    
  Abstraction is about hiding complexity behind a simple contract: abstract/interface. It's the "what you can ask it to do".
    
  They work together, but if a test asks you to "show abstraction", it wants an abstract class or an interface.

    Naming convention: interfaces start with I, such as IShape, IHealable and INotifier. (Newer C# versions allow default method bodies in interfaces, but tests rarely need them.)
    

  
    📝 How to explain it in a test answer
    
  "Abstraction means exposing only the essential features of an object while hiding its implementation details. In C# this is done with abstract classes and interfaces, which define what must be done, while subclasses decide how. For example, Shape declares abstract double Area(), and Circle and Rectangle each implement it. Benefit: code that uses a Shape works with any shape without knowing the formula, and it cannot create an incomplete Shape."
    

  
    ⚠️ Common mistakes
      
    
    • Giving an abstract method a body: public abstract double Area() { } ❌. End it with a semicolon instead.
      • 
    
    • Declaring an abstract method in a class that isn't marked abstract. This gives error CS0513.
      • 
    
    • Forgetting public when implementing an interface method. This gives error CS0737.
      • 
    
    • Forgetting override when implementing an abstract method. This gives error CS0534: "does not implement inherited abstract member".
      •

    🧩 Exam Problems: new scenarios
    
  
    Test questions won't be about Characters and Shapes. These problems use new topics so you practise turning a story into classes. Use the 5-step method first, then code.
    
  
    
    
    The 5-step method for ANY OOP problem
    
    
      
      
    1. Nouns become classes. Underline the things in the story: Car, Truck, CarPark.
      2. 
      
    2. "X is a kind of Y" means inheritance. Find the shared parent: Car and Truck are both kinds of Vehicle.
      3. 
      
    3. "Each type does it differently" means polymorphism. Use a virtual/abstract method in the parent and override it in each child.
      4. 
      
    4. "Should never exist on its own" means abstraction. Make the parent abstract. If unrelated classes share an ability, use an interface.
      5. 
      
    5. Rules ("must not", "only between", "cannot change") mean encapsulation. Use a private field plus a checked property or method.
      6.
